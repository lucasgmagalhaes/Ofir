# 0019. The standard library is written in Astra, from stage 0 on

- Status: Accepted
- Date: 2026-10-31

## Context

The first stage 0 compiler implemented the methods of the primitive types
(`s.len()`, `s.push(t)`, `n.abs()`, `x.sqrt()`, ...) as a table inside the
compiler, with their bodies generated by the compiler or written in the C
runtime. Every such function is work to redo when the library moves to
Astra, the compiler grows a special case for each one, and the runtime
becomes more than "what cannot be written in Astra" (runtime design, 1).

The specification declares methods inside the body of their type (ADR
0015), but a primitive type has no declaration to hold them.

## Decision

- `std/` is Astra code from stage 0 on. `std/core` is the prelude: its
  public declarations are visible in every module without an import
  (spec 7.4).
- A primitive type's methods are declared in `std/core` with `@lang`:

  ```astra
  @lang("str")
  pub struct str {
      ptr: *u8
      len: int
      cap: int

      pub fn len(self) int { return self.len }
  }

  @lang("i64")
  pub copy struct i64 {
      pub fn abs(self) Self { return if self < 0 { -self } else { self } }
  }
  ```

  The declaration does not create a type: its body is attached to the
  primitive. For `str`, the fields give its layout, which the compiler
  checks against the one it uses; numeric types declare no fields.
  `@lang` is allowed only in `std`.
- Operations that only the compiler can generate (arithmetic without the
  overflow check, LLVM intrinsics such as `llvm.sqrt`, saturating casts)
  are functions without a body in an `extern "intrinsic"` block, allowed
  only in `std`. The compiler recognizes them by name and lowers each call
  to the LLVM operation; unlike `extern "C"` functions, they are safe to
  call:

  ```astra
  extern "intrinsic" {
      fn wrapping_add_i64(a: i64, b: i64) i64
      fn sqrt_f64(x: f64) f64
  }
  ```

- Until generics, three methods stay built into the compiler because their
  signature needs a type argument or a pointer element type:
  `x.wrappingCast<T>()`, `x.saturatingCast<T>()` and `p.add(n)`; the
  constants `I.MIN`, `I.MAX`, `F.NAN`, `F.INFINITY` and `F.EPSILON` too.

- The C runtime keeps only the process entry, panics, allocation and the
  system interface; `std` reaches it through `extern "C"` declarations.

## Consequences

- Stage 0 needs modules, `extern "C"`, `unsafe` and raw pointers before the
  rest of phase 2 (generics, collections): the roadmap is reordered.
- The compiler loses its table of built-in methods; adding a library
  function no longer touches the compiler.
- The methods of the eight integer types are written once per type until
  generics with bounds and interfaces (stage 1) let one declaration cover
  them all; a script in `tools/` generates them.
- LLVM inlines the small library functions, so generated code is as fast
  as with built-ins; the benchmarks of generated code check it.
- The prelude is parsed and checked in every compilation, which the
  compiler benchmarks measure.
